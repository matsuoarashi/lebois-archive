# le bois 日報

清澄白河のボタニカルカフェ **le bois** の、閉店後の日報を1つにまとめる仕組み。
在庫・売上・レジ締めを、スマホで数分で終わる5ステップにしています。

**デモを触る → https://matsuoarashi.github.io/lebois/**
（Pagesを有効にすると、このURLで動きます）

---

## なにをする道具か

いま le bois では、閉店後にスタッフがLINEへ3つのことを手で投稿しています。

- 在庫数（4品目 × 冷凍／冷蔵／廃棄）
- 売上（Squareの画面のスクリーンショット）
- レジ金（金額だけ）

手間のわりに、あとから使えるデータが残りません。売上はスクショなので集計できず、
レジ金は理論値と照合されないので、合っているかどうか誰にも分かりません。

この仕組みは、**入力を増やさずに、照合と蓄積を足します。**

## 考え方

### 在庫は「照合」する

解凍（冷凍から冷蔵に移すこと）は、合計を変えません。だから合計の理論値は
Squareの販売数と発注表の入荷だけで出せます。

```
あるはずの合計 ＝ 前日の合計 ＋ 入荷 − 販売数
差             ＝ 数えた冷凍 ＋ 数えた冷蔵 − あるはずの合計
```

スタッフは今までどおり数えるだけ。合っていれば何も聞かれません。
ズレた品目だけ「廃棄したか／わからないか」を聞き、廃棄は報告文に、
不明分は差異として記録します。

**解凍を入力させる設計は採用しませんでした。**数えた実数から逆算できるうえ、
解凍は朝や昼にやって報告は夜なので「思い出す」作業になり、忘れやすいからです。

### 在庫は個数で持ち、本数は表示で出す

冷凍庫は本数（ロール数）で数えますが、記録は個数（切れ・個・食）に統一します。
減るときは必ず個数だからです。半端も表現できます。

| 品目 | 記録 | まとまり | 換算 |
|---|---|---|---|
| チーズケーキ | 切れ | 本 | 1本 = 7切れ |
| ガトーショコラ | 切れ | 本 | 1本 = 9切れ |
| シフォンケーキ | 個 | ロール | 1ロール = 8個 |
| クロックムッシュ | 食 | — | — |

表示は「冷凍70切れ（10本）」のように併記します。

### 5ステップ

| | 画面 | 本番での扱い |
|---|---|---|
| 1 | 今日のデータ | Square＋発注表から自動。見るだけ |
| 2 | 在庫を数える | 数えて入れる |
| 3 | 差の確認 | 合っていれば出ない |
| 4 | レジ金 | 金額を1つ |
| 5 | 送信 | LINEに貼る文章ができる |

## この中身

```
├── docs/index.html   GitHub Pages で動くデモ版（保存はブラウザだけ）
├── gas/
│   ├── Code.gs       Apps Script のサーバー側（スプレッドシート＋Square）
│   ├── Index.html    同・画面（build.py が生成）
│   └── SETUP.md      スプレッドシートに組み込む手順
├── src/
│   ├── ui.css        画面のスタイル（ここが唯一の原本）
│   ├── ui.js         画面のロジック（ここが唯一の原本）
│   ├── store-local.js  保存先アダプタ：ブラウザ
│   ├── store-gas.js    保存先アダプタ：スプレッドシート
│   └── seed.json     初期在庫
└── build.py          src から docs/ と gas/ を生成
```

画面のコードは `src/` の1か所にしかありません。デモ版と本番版の違いは
**保存先アダプタ（`STORE`）だけ**です。片方だけ直してしまう事故が起きません。

```bash
python3 build.py     # docs/index.html と gas/Index.html を作り直す
```

## デモを公開する

1. このリポジトリをGitHubに置く
2. **Settings → Pages → Source: Deploy from a branch**
3. Branch: `main`、フォルダ: `/docs` → Save
4. 1〜2分待つと `https://matsuoarashi.github.io/lebois/` で開けます

デモ版の入力は**その端末のブラウザにだけ**残ります。誰かと共有されることはありません。
Squareにも繋がっていないので、売上は手で入れる形になります。

### 実データの読み込みリンク

Squareのアクセストークンを設定するまでのあいだ、URLの `#d=` にデータを載せて
フォームを開くことができます。開くと在庫・釣銭・売上・売れたもの・入荷が入った状態になります。

```
https://matsuoarashi.github.io/lebois/#d=<base64url(JSON)>
```

JSONの形:

```json
{
  "note": "画面に出すひとこと",
  "float": 36740,
  "stock": {"cheese": {"fz": 28, "ch": 9}, "gateau": {"fz": 36, "ch": 5},
            "chiffon": {"fz": 6, "ch": 0}, "croque": {"fz": 14, "ch": 2}},
  "sales": 49237,
  "cash": 3790,
  "items": {"チーズケーキ": 12, "ガトーショコラ": 3},
  "arrivals": {"cheese": 3, "gateau": 1}
}
```

`stock` は在庫の出発点、`arrivals` は入荷（本／ロール／食）。すべて省略可能です。
Apps Script版でSquareと繋いだあとは、この仕組みは使わなくなります。

## 本番として使う

`gas/SETUP.md` の手順どおりに進めてください。既存の製造予定表スプレッドシートに
シートを足し、Apps Scriptをウェブアプリとして公開します。

Square連携は後回しでも動きます（その間は売上を手入力）。

画面の文言は保存先アダプタが決める `LIVE` フラグで切り替わります。
`store-gas.js`（本番）は「自動で埋まっています」、`store-local.js`（デモ）は
「本番では〜」と試用版の注意書きを出します。

## 分かっている制約

- **Squareの現金管理はスマートフォンでは使えません。**レジ締めをSquareターミナルで
  行えば、理論値・差異をSquare側から取得できます。それまでは釣銭準備金を設定値として
  持つ方式で運用します。
- **Squareの在庫機能は冷凍／冷蔵の2状態を持てません。**また在庫履歴の閲覧は
  リテールPOSレジ プラス（有料）が必要です。在庫台帳をスプレッドシートに持つのは
  この2点が理由です。
- **同じSquareアカウントに複数店舗があります。**集計は必ず店舗（location）で
  絞ります。同名商品が別店舗にあるため、商品名だけで集計すると混ざります。
- **LINEへの自動投稿は入れていません。**Messaging APIはグループ送信を人数分として
  カウントするため、13人のグループに毎日1通で無料枠（200通/月）を超えます。
  コピーして貼る運用にしています。

## この先

日次ログが溜まると、次ができるようになります。

- 週次の販売本数を自動集計（いまスプレッドシートで手作業。2026年4月末で更新が止まっています）
- 廃棄率・棚卸差異の推移
- **木曜の発注期限に、販売ペースと冷凍在庫から翌週の発注数を提案する**

最後のものが本命です。発注は木曜締めで翌週の水曜・土曜の2回ぶんをまとめて決めており、
いまは勘と記憶で判断しています。
